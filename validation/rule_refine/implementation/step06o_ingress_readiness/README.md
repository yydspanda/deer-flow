## 为什么不直接发送先前的3条人工告警

原项目`flow_task_router`调用可选监测后仍会进入`create_work_flow_task`，派发原`agent_task`并写业务数据库。源码包`tasks/task_util.py`的成功/失败钩子会调用Zeus回调，没有LOCAL自动跳过。因此人工请求也可能进入原研判及回调，不是一次独立规则建议试调用。

6N的人工topic/rule不在911条CSV中，不能登记为正式规则；入口和后台目前使用计数器默认最小数量1000，3条也不会触发建议。虽然计数器构造参数可设置，当前持久监测配置没有阈值字段；本步骤不补造真实规则身份、不灌1000条样本、不修改正式阈值。

源码包中的注入脚本SHA为3361f29d5170e9408e0494b2e266c0e3c4bb41b349023e0c7387584dc6b8c58d。它复制内嵌的同一告警，改写随机ID（或给定起始ID后递增），强制executeType=3，默认提交5条，并非从PKL抽取独立真实样本。不能用改ID后的数量代表真实突增；本次先核对内网版本，不依据源码包盲目执行。

在小样本中找到可用规则及来源后，下一步才准备一条真实历史告警的联调方案。实际POST仍涉及原完整研判及Zeus回调，需明确实际环境和测试来源后执行；单条入口验证不会被记为已经达到突增阈值或完成自动分析，历史样本按规则分布也不是当前小时告警量。
