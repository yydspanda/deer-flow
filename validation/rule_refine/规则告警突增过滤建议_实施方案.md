# 规则告警突增过滤建议实施方案

更新日期：2026-11-02。当前：[6X历史规则试跑](implementation/step06x_historical_review/README.md)已完成并收到报告正文：passed/insufficient_evidence，无校验或传输错误。50条目标告警/51条日志均符合材料条件，按128KiB完整请求预算实际纳入11条告警/11条日志，输入127026字节；1次SDK请求耗时78.075秒，56675tokens。报告指出9条样本集中于同一签名、目标IP和端口，其余两条为其他签名；模型因业务属性未确认及样本范围有限，给出核查方向而未生成过滤条件。代码未要求必须取得资产或EDR证据才能提出带前提的建议；此次是模型主动选择证据不足。保留原结果，优先核实集中场景的业务用途，不自动扩大预算、改状态或重调模型。此前6W安装与重启idle已确认；真实突增后的Celery自动建议、运营效果及Zeus接口联调仍待验证。

实施项目是内网的 **sec_know_model**。本地 `validation/sec_know_model.zip` 用于对照源码；具体修改以用户随后提供的内网实际版本为准。

目标是：**发现某条规则告警突增，自动分析具体场景与当前规则，给出运营能够理解、ZEUS 能够接收的过滤条件建议。**

## 1. 已确认的范围

业务流程保持简单：

```text
收到告警 → 按规则统计突增 → 获取规则与代表告警
        → 分析原因 → 生成过滤条件建议 → 保存并展示
```

- 使用原项目的告警接收、后台任务和存储能力，优先复用 FastAPI、Celery、Redis、SQLAlchemy；具体接入位置在步骤 0 核实。
- 先用 CSV 替代规则配置查询，用本地保存替代 ZEUS 建议接收。两个 ZEUS 接口目前尚未提供。
- 告警量、时间和样本来自已接收告警或独立历史回放。CSV 只有配置，不能据此生成真实突增统计。
- 重点输出“哪里有问题、为什么、具体怎么改”。不要求先建设完整监控大屏。
- 建议由运营确认后采纳，不自动修改规则。实际降量和算力节省在上游应用规则后验证。
- 分析编号由系统生成和维护；用户不需要手工填写轮次或分析编号来串联步骤。
- 规则引擎的去重有效期、窗口触发方式和原配置 `threshold` 含义，不在本次过滤建议的修改范围内。本功能的监测阈值单独配置。

## 3. 当前 mock 与后续 ZEUS 的替换关系

| 能力 | 当前实现 | 后续实现 |
|---|---|---|
| 获取规则配置 | 按企业、topic、rule_code 从 CSV 读取 | 调用 ZEUS 配置查询接口 |
| 获取告警样本 | 原项目已接收数据或独立历史回放 | 继续复用；缺少详情时通过 ZEUS 补充 |
| 提交建议 | 保存本地结果，模拟接收回执 | 调用 ZEUS 建议接收接口 |
| 突增监测、分析与校验 | 原项目内新增能力 | 沿用同一套逻辑 |

封装两个可替换的边界：“获取分析材料”和“提交建议”。CSV、本地接收与未来 HTTP 实现采用相同输入输出结构，不把 CSV 读取逻辑写进模型分析流程。

拟议的 ZEUS 接口如下，路径待双方联调确认，不表示当前已经存在：

| 方向 | 接口 | 内容 |
|---|---|---|
| sec_know_model → ZEUS | `POST /api/rule-analysis/context` | 传规则身份、时间范围和样本引用，取配置版本、配置及必要详情 |
| sec_know_model → ZEUS | `POST /api/rule-analysis/recommendations` | 提交问题、证据和结构化建议，取得接收回执 |

本地接收回执明确标记 `delivery_mode=mock`。本地保存成功不表示 ZEUS 已接收，更不表示规则已应用。

## 4. 建议格式

外层保留规则身份、配置版本、问题、建议、证据和系统编号；条件主体沿用用户提供的格式。下例仅说明结构，数量和字段值不是实测结果：

```json
{
  "schema_version": "sec_know.rule_filter_recommendation.v1",
  "recommendation_id": "系统自动生成",
  "company_code": "企业标识",
  "rule_code": "对应规则编号",
  "rule_name": "对应规则名称",
  "rule_config_version": "分析所用规则配置的摘要",
  "issue": "突增告警集中在某个重复业务场景，现有条件尚未排除该场景",
  "recommendation": "确认该场景属于正常业务后，增加以下组合排除条件",
  "certainty": "场景特征有样本支持，正常业务属性仍需运营确认",
  "evidence": {
    "window_start": "2026-10-26T09:00:00+08:00",
    "window_end": "2026-10-26T10:00:00+08:00",
    "alert_count": 2000,
    "count_basis": "received_unique_alerts",
    "sample_alert_ids": ["告警ID1", "告警ID2"]
  },
  "change_type": "add_exclusion",
  "filter": {
    "topic": "sec_guard",
    "A": {"name": "字段名1", "value": "aaaa", "operator": "equal"},
    "B": {"name": "字段名2", "value": "bbb", "operator": "contain"},
    "C": {"name": "字段名2", "value": "ccc", "operator": "notcontain"},
    "expression": "B&&(A||C)"
  },
  "automatic_apply": false
}
```

### 4.1 新增排除条件

`change_type=add_exclusion` 时，`filter.expression` 为真表示命中建议排除的场景。采纳后的概念关系为：

```text
原规则触发条件 && !(建议排除条件)
```

这是新增排除场景的语义约定，不直接作为 ZEUS 可导入配置。转换成 ZEUS 原生条件组时要验证组合关系。

### 4.2 修改已有条件

修改已有条件时使用另一种修改类型，例如 `modify_conditions`，提供目标条件组 `target_term_alias`、修改前内容和建议片段。沿用原报告的 `suggestion_fragments`，其中可包含 `term_alias`、`when`、`matchType`、`customRelation` 或原生条件字段。

这一类型不能一律套用新增排除条件的取反公式。例如修正原规则中的“或/且”关系，应保留该条件组原来的触发语义。存在多个业务意图备选时，只提出待确认方案，不自动选择一种。

### 4.3 条件解释与结果状态

- `name` 使用对应 topic 实际支持的字段名，不由模型猜测不存在的字段。
- 明确 `equal / contain / notcontain` 与 ZEUS 原操作符的映射，以及大小写、字符串/集合、缺失值和空值语义。当前格式参考本身不能证明这些语义已一致。
- `expression` 只允许约定的别名、括号和布尔运算符，使用受限解析器，不执行模型返回的任意代码。
- 缺失字段或不支持的语义不能当作确定的可过滤匹配；本地试算标为未知，留待核对。
- 输入文件中的特殊缩进空格不继承到输出，统一用标准 JSON 序列化生成。
- 分析结果区分“有具体修改建议”“暂无修改建议”“证据不足”；执行失败另记失败原因并允许重试。
- 第 4 步 B 增加明确的 needs_existing_condition_change 状态：发现需要修改原条件时说明位置与方向，在相应修改契约实现前不强行生成新增排除条件。proposal 仍只使用既有 add_exclusion 契约。
- 保存规则来源、告警来源和交付模式，区分 CSV 快照、历史回放、实时接收、模拟输出与真实模型结果。

### 步骤 0 的最小信息

先确认以下信息，再按实际操作系统给可直接执行的命令：

1. 项目根目录、操作系统、终端类型；是在开发环境还是运行容器内操作。
2. Python 版本及实际使用的虚拟环境。
3. Git 当前分支/提交和工作区是否有修改；如果没有 Git，说明源码版本来源。
4. 顶层目录，以及 `service`、`tasks`、`model`、`my_workflows` 等相关目录是否存在。
5. CSV 在内网的路径；可用告警数据是已有数据库记录、导出文件还是接口接收数据。

这一步只检查，不启动任务或调用模型。无需贴 `.env`、令牌、数据库密码、全量数据库或原始告警内容。

### 步骤 2 的配置读取要求

- 用户已将 CSV 放到 `$HOME/sec-rule-refine-data/rules.csv`，文件 SHA-256 和 911 条记录均已核对通过，与源码目录分开放置。
- 配置身份按实际企业作用域、topic、rule_code 匹配，必要时使用规则原生 ID；不得把跨企业的同名规则混在一起。
- CSV 的 `terms`、`relation`、`custom_relation` 等保持原始结构并保留来源。
- 已确认 `terms` 内的 `config`/`standard_field_config` 还可能是 JSON 字符串；只解析已确认的 JSON 字段，并保留原始行。`duplicate_removal` 存在非 JSON 文本；不得对所有字符串统一尝试 JSON 转换。个别条件组的 alias/index 为 null，读取时不得擅自补造身份。
- `standard_status`、原字段与标准字段配置哪个生效，需要核对原项目实际实现。未确认时保留两份并说明未知，不能擅自选择一个执行分支。
- 首版配置版本对完整原始行按键排序计算摘要，前缀为 `csv-row-v1:sha256:`。保守保留审计等所有原字段，不遗漏未知字段作用；字段内容变化会更新版本。文件路径和数据行号不参与该版本，CSV 文件摘要另行记录。这是快照版本，不宣称语义等价。
- mock 不要求先启动一个额外服务；通过相同调用契约的本地实现即可。后续用 HTTP 契约测试核对请求和响应。

### 步骤 3 的计数要求

- 源码 ZIP 显示 `/workflow/task` 接收 `WorkFlowTaskInput` 后创建任务；当前实现先派发 Celery，再写任务表。任务表可用于历史样本，不能声明它覆盖全部接收请求。完整证据见 [第 3 步入口核对](implementation/step03_ingress_check/README.md)，上线接入前核对内网实际版本。
- 命中规则来自 `alert_data.alert.hitLog[*].topic/ruleCode`，不能用 `profileCode` 代替；关联告警不作为本次新接收告警。外层 `alert_id` 与内层 `alert.alertId` 的一致性需要检查。
- 接口 `app_code` 是子系统编码，不能直接作为规则配置的 `company_code`。用户已选择按 topic + ruleCode 唯一匹配 CSV，取配置 company_code 作为统计归属；匹配歧义时不默认选第一家公司，也不把配置归属当资产身份或授权证明。
- 早期第 3 步 A 的 live 要求显式企业；第 3 步 D 按用户批准的方案改为统一 RuleConfigSource 查询，唯一匹配提供规则配置归属，来源标记 rule_config_unique_match，实际提供器保存在 rule_source.kind。当前提供器为 CSV mock，正式来源是后续 ZEUS API；零条/多条匹配跳过并记录，显式企业约束仍保留。
- 稳定去重键排除时间、会话、flow 和配置版本；第 3 步 B 才负责持久去重、首次接收时间和窗口计数。独立回放使用系统生成的外层存储命名空间，不仅靠 mode 隔离。
- 第 3 步 B 内网已发现 EVAL 不可用，改用原项目 `util/model_semaphore.py` 的 WATCH/MULTI/EXEC 模式，监视三键、有限重试、一起提交去重、两窗口计数和待处理信号；同一规则已有未确认信号时继续计数但不另建信号。真实派发与确认在后续步骤接入，不只依靠瞬时 triggered=true。
- 当前窗为 `(t-W,t]`，前窗为 `(t-2W,t-W]`。观察覆盖满 2W 且前窗非零时判断增长倍数；否则达到数量阈值记 high_volume，不宣称已证明突增倍数。live 使用 Redis TIME，demo/replay 用指定时间。
- 第 3 步 D 保留原 WATCH 连接，另用同一主数据源的非事务 pipeline 分两批读取，减少网络往返；不在原 WATCH pipeline 中途 execute。单次最多两条池连接；源数据或连接故障不能伪装成功。
- 第 3 步 E 在同步 `/workflow/task` 的参数构造之后、原任务创建之前加入默认关闭的可选调用；统计接收并成功登记的去重告警，包括随后任务创建失败的请求。每进程最多 4 个监测请求，单请求最多 8 条规则与 1 秒软预算；降级、未开始和提交结果不确定均显式记录，不能把降级时的登记量称作全量。独立 Redis 客户端同地址、0.5 秒连接/读取超时、不自动重试；异常及兜底日志异常都不改变原任务返回。此步不派发或确认信号，不修改 `.env`。
- 默认值为 1 小时窗口、1000 条、3 倍、1 小时冷却、24 小时去重保留期。类构造器支持参数，但截至6V实际入口/后台没有接入配置字段，运营当前不能通过本地配置修改；此前“均可配置”的表述不准确。第 3 步 G 已通过本地配置启用入口监测，真实登记已由6Q确认。测试专用设置为 10 秒、3 条、2 倍、10 秒、60 秒，不替代正式配置。去重仅在保留期内有效，过期告警 ID 可能再次计数。
- 按企业、topic、rule_code 隔离；同一告警对同一规则只记一次。
- 一条告警命中多个规则时，可以分别计入对应规则，但各规则数量相加不是独立告警总数。
- 记录使用接收时间还是事件时间，以及窗口边界；回放采用独立模式，不能污染实时窗口。
- 本服务只收到部分告警时，数量注明“本服务接收的去重告警量”，不宣称 ZEUS 全量。
- 统计窗口、最小数量、增长幅度和再次触发间隔可配置。历史不足/零基线时不计算失真的增长倍数，只说明高量触发。
- 入口计数不能依赖模型是否成功、任务是否最终完成。采集/统计失败要可见；不要直接把成功任务表当接入总量。
- 同次突增合并为后台分析任务，控制模型并发、样本量和重试次数，复用原项目队列能力。

### 步骤 4 与 5 的证据要求

- 第 4 步 A 先通过共享 RuleConfigSource 和信号样本引用组装材料，使用人工任务验证，不写业务库、不发模型调用。内网 LOCAL 任务表已确认为空，不能把无样本表述为读取成功或真实材料覆盖。实现与命令见 [材料组装](implementation/step04a_materials/README.md)。
- 代表样本覆盖主要场景和时间段，先做聚合和去重，不把全部告警原文送入模型。
- 同 rule_code 不等于同一行为。建议根据来源、接口、进程、操作等实际证据限定场景。
- 复用已有研判和人工反馈时区分来源；模型建议忽略不等于已经证实正常业务。
- 可以提出已知条件逻辑失效的修正，也可以提出缺失场景的过滤条件。业务正常性未确认时把前提写在建议中。
- 样本试算展示分子、分母、未知项和匹配引用，称为“样本匹配情况”；不直接称误报率、整体降量率或准确率。
- 本地规则解释器未覆盖的操作符/字段类型明确标为不支持；本地试算不冒充 ZEUS 引擎回放结果。
- 第 5 步拆分交付：5A 只做提供日志上的纯函数试算，支持字符串 equal/contain/notcontain、&&/||/括号；按单条日志求值，不跨日志拼接条件，不把匹配日志数换算成可忽略告警数。缺失/null/非字符串字段使用未知值参与组合运算。完整输入范围、版本核对和模型材料关联放在 5B 串联时处理。CSV 不是完整 topic 字段目录，也不能证明 ZEUS 引擎语义一致。
- 5B 通过重建当前提示词核对已有分析的版本、摘要与来源；建议的规则身份、窗口、数量和引用样本须与该材料一致。只在模型实际看到的日志上试算，每个引用告警至少有一条明确匹配日志；单列未取得、全部省略和部分省略的样本。通过注入的工厂重新读取配置，比较规则版本和内容；来源切换、内容改变、查询失败不沿用旧配置。通过时保留原建议 ID，标记 reviewable（待运营审阅），不代表已审批或线上应用。未来后台交付须通过此检查，当前本步仍是独立人工测试。
- 6V正式补丁让分析支持检查和组合试算共享数字equal比较；字符串保持原语义，数字contain/notcontain及bool等仍为未知。候选材料上限3MiB，兼容既有4MiB保存包；去掉8KiB单日志与64KiB日志组的提前淘汰，完整messages按128KiB选取整条日志，记录预算省略且不截断字段。旧提示词产物不会自动转成新成功记录，旧待办也不自动重新请求模型。
- 6W进一步替代上述6V预算：输入128KiB/输出64KiB/超时240秒/尝试总次数3/间隔60秒集中到limits本地配置，可按README范围调整。候选32MiB、单告警与旧回答2MiB、保存40MiB，去掉固定节点数及规则32KiB/旧回答入模2KiB门槛；整条日志优先，历史研判占剩余请求预算。不支持的本地比较有字段依据时保存manual_review，不生成已验证的正式建议；缺字段、身份和引用错误仍失败。样本20/每样本3日志等边界保留。

### 步骤 6 的交付与恢复

- 6A 先保存不可变分析包，再提供只读已有分析的交付函数；不在交付重试中生成建议。记录标识按完整内容摘要产生，重复保存相同内容使用同一记录；不同分析保留为不同记录，不覆盖旧证据。这不是后台按信号去重的替代，生成任务去重由后续后台步骤负责。
- 每次交付重新执行 5B，并先保存检查与尝试记录，之后才提交到 LocalRecommendationSink；接收异常或回执不符标记交付未确认，不能推断接收端没有保存。结果写盘失败直接报错，重试沿用已保存建议 ID，由接收端去重。
- 保存各次尝试及回执，不覆盖历史；后续配置变化只影响新尝试，不能抹掉旧接收事实。本地接收始终标为 mock/applied=false。
- 后续再接后台信号派发、样本读取、生成并发/重试、确认信号和运营可读报告；6A 本身不确认 Redis 信号，不启动模型请求。
- 6B 用同一流程入口串联上述模块。稳定信号身份定位处理目录，完整输入另存并拒绝同身份换内容；本机文件锁防止同信号并发生成。分析前保存开始记录和材料，分析后先保存完整结果再建索引。交付重试自动找回原分析，不让用户手工传编号；有开始记录但无完整结果时标为 analysis_unconfirmed，不自动重调模型。材料读取故障发生在分析之前，可再次尝试。当前仅本地 mock 串联，后续仍需接既有后台任务、真实材料和信号确认。
- 6C 新增 LOCAL SQLite 只读任务读取器，按应用、流程和最多 20 个信号引用告警查询，保留所有状态与重复版本，不按任务创建时间冒充接收窗口。超过 100 行或 8 MiB 返回材料上限时明确失败，不截取部分版本。原告警无效时保留异常行，由 4A 排除该样本；可选历史响应无效时保留原告警并记录 stored_response_omitted。末尾诊断只读取最近任务引用并输出数量，不产生突增信号或模型请求。
- 6D 将 pending → SignalProcessor → acknowledge 串成一次调用，按模式、命名空间和规则作用域校验信号。任务尚未提交时返回 materials_pending，材料全部不可用时返回 materials_unavailable；二者都在分析开始记录之前结束，不固化空材料。完整输入、分析内容和交付结果均核对已落盘后才按原 signal_id 确认；确认超时为 ack_unconfirmed，不断言信号仍在。交付重试复用原分析。此步人工计数器测试不代表后台调度、真实 Redis 消费已上线。


- 6E 先只读核对启动方式：原源码包包含 local_run.sh、local_run.detector.sh，没有用户口述的 run_local.sh。local_run.sh 启动 tasks.task.app、单并发 periodic_queue worker 和独立 beat，但不消费 default 队列。内网实际版本、可见进程及所属项目需核对，不能直接照源码启动脚本或重复起 worker。
- 6F 新增后台适配与轮转执行器：任务注册到 tasks.task.app，LOCAL beat 每30秒向 periodic_queue 发一个 expires=25秒的 tick；代码安装时独立分析配置默认关闭。后台复制环境后读取监测配置，验证环境变量及已加载应用均为LOCAL，固定本机SQLite和本机模型代理；在分析开始记录之前取得原共享模型并发槽。每tick查询当前目录最多256个作用域、只处理一个信号，固定所读快照并按原身份确认。持久游标轮转，60秒间隔，最多3次尝试后保留信号并暂停该信号自动重试；模型槽繁忙不消耗次数，已阻断/分析未确认立即暂停。显式重置只解除后台重试暂停，不删除原分析或自动重新生成。内网已回传适配测试、演示及独立Celery注册通过；启用、broker及真实模型链路仍待验证。规则目录移除后的旧信号不在当前枚举范围。
- 6W替代上述失败恢复行为：明确模型失败按配置建新attempt，成功交付补投沿用原分析；次数耗尽先保存分析、交付与finalized记录并复读一致，再确认待办。开始后未收到响应/未完整保存结果保持unconfirmed，不自动重发。CLI按规则或all显式retry/release，旧失败升级不静默重调。维护扫描与动作使用同一scheduler锁，SET NX和条件确认保留新pending；纯材料等待不消耗失败次数，部分材料可继续并记录缺失。入口计数不被维护命令改变。
- 6G 在分析关闭状态验证真实调度：原local_run.sh终端Ctrl+C后等待全部子进程退出，检查版本、开关及同应用旧进程，再按原脚本以LOCAL重启。API和代理不重启，不另起脱离原脚本管理的worker/beat。贴回beat定时派发与worker的analysis_disabled日志，之后再进入分析启用。原beat启动还会派发既有Skills同步，不能将后台重启称为零外部操作。
- 6H 在另一个终端显式ENABLE自动分析，只原子更新独立配置，worker下次tick重读，无需重启。脚本核对终端LOCAL、监测配置、CSV及模型策略，不执行后台消费作为预检；连通性和实际材料仍以后台输出为准。DISABLE关闭下一次分析，不中断已开始调用，不清除任何信号或证据。
- 6I 先复用已安装的`test/rule_refine/check_local_task_source.py`只读确认当前LOCAL样本。6H的idle证明规则目录及Redis待办查询工作，但没有进入任务表取样和模型请求。检查只筛选zeus/alert_agent的最近20条任务引用，不代表全量数据质量；有材料再准备少量隔离回放，仍为空则确认内网已有JSON或数据文件。源码包的test_zeus_alert.py依赖包外PKL并会调用/workflow/task进入原研判，不能直接用整套测试或灌1000条请求来验证计数。
