## 1. 已确认的范围

业务流程保持简单：

```text
收到告警 → 按规则统计突增 → 获取规则、本次样本和突增前最近20条历史
        → AI生成过滤建议 → AI独立上下文复核 → 保存并展示
```

- 使用原项目的告警接收、后台任务和存储能力，优先复用 FastAPI、Celery、Redis、SQLAlchemy；具体接入位置在步骤 0 核实。
- 先用 CSV 替代规则配置查询，用本地保存替代 ZEUS 建议接收。两个 ZEUS 接口目前尚未提供。
- 告警量、时间和样本来自已接收告警或独立历史回放。CSV 只有配置，不能据此生成真实突增统计。
- 重点输出“哪里有问题、为什么、具体怎么改”。不要求先建设完整监控大屏。
- 建议由运营确认后采纳，不自动修改规则。实际降量和算力节省在上游应用规则后验证。
- 分析编号由系统生成和维护；用户不需要手工填写轮次或分析编号来串联步骤。
- 规则引擎的去重有效期、窗口触发方式和原配置 `threshold` 含义，不在本次过滤建议的修改范围内。本功能的监测阈值单独配置。

## 3. 当前 mock 与后续 ZEUS 的替换关系

| 能力 | 当前实现 | 后续实现 |
|---|---|---|
| 获取规则配置 | 按企业、topic、rule_code 从 CSV 读取 | 调用 ZEUS 配置查询接口 |
| 获取告警样本 | 原项目已接收数据或独立历史回放 | 继续复用；缺少详情时通过 ZEUS 补充 |
| 提交建议 | 保存本地结果，模拟接收回执 | 调用 ZEUS 建议接收接口 |
| 突增监测、分析与校验 | 原项目内新增能力 | 沿用同一套逻辑 |

封装两个可替换的边界：“获取分析材料”和“提交建议”。CSV、本地接收与未来 HTTP 实现采用相同输入输出结构，不把 CSV 读取逻辑写进模型分析流程。

拟议的 ZEUS 接口如下，路径待双方联调确认，不表示当前已经存在：

| 方向 | 接口 | 内容 |
|---|---|---|
| sec_know_model → ZEUS | `POST /api/rule-analysis/context` | 传规则身份、时间范围和样本引用，取配置版本、配置及必要详情 |
| sec_know_model → ZEUS | `POST /api/rule-analysis/recommendations` | 提交问题、证据和结构化建议，取得接收回执 |

本地接收回执明确标记 `delivery_mode=mock`。本地保存成功不表示 ZEUS 已接收，更不表示规则已应用。

### 4.1 新增排除条件

`change_type=add_exclusion` 时，`filter.expression` 为真表示命中建议排除的场景。采纳后的概念关系为：

```text
原规则触发条件 && !(建议排除条件)
```

这是新增排除场景的语义约定，不直接作为 ZEUS 可导入配置。转换成 ZEUS 原生条件组时要验证组合关系。

### 4.2 修改已有条件

修改已有条件时使用另一种修改类型，例如 `modify_conditions`，提供目标条件组 `target_term_alias`、修改前内容和建议片段。沿用原报告的 `suggestion_fragments`，其中可包含 `term_alias`、`when`、`matchType`、`customRelation` 或原生条件字段。

这一类型不能一律套用新增排除条件的取反公式。例如修正原规则中的“或/且”关系，应保留该条件组原来的触发语义。存在多个业务意图备选时，只提出待确认方案，不自动选择一种。

### 4.3 条件解释与结果状态

- `name` 使用对应 topic 实际支持的字段名，不由模型猜测不存在的字段。
- 统一使用 `Eq / Ne / Contains / NotContains / StartsWith / EndsWith`；仍需在接口联调核对大小写、字符串/数字、缺失值、空值及表达式语义。离线比较器通过不证明ZEUS引擎语义已一致。
- `expression` 只允许约定的别名、括号和布尔运算符，使用受限解析器，不执行模型返回的任意代码。
- 缺失字段或不支持的语义不能冒充确定的过滤依据。6Z仅检查输出格式、引用、字段名和表达式，由AI复核建议；不运行过滤试算或计算降量率。
- 输入文件中的特殊缩进空格不继承到输出，统一用标准 JSON 序列化生成。
- 分析结果区分“有具体修改建议”“暂无修改建议”“证据不足”；执行失败另记失败原因并允许重试。
- 第 4 步 B 增加明确的 needs_existing_condition_change 状态：发现需要修改原条件时说明位置与方向，在相应修改契约实现前不强行生成新增排除条件。proposal 仍只使用既有 add_exclusion 契约。
- 保存规则来源、告警来源和交付模式，区分 CSV 快照、历史回放、实时接收、模拟输出与真实模型结果。

- 5B 通过重建当前提示词核对已有分析的版本、摘要与来源；建议的规则身份、窗口、数量和引用样本须与该材料一致。只在模型实际看到的日志上试算，每个引用告警至少有一条明确匹配日志；单列未取得、全部省略和部分省略的样本。通过注入的工厂重新读取配置，比较规则版本和内容；来源切换、内容改变、查询失败不沿用旧配置。通过时保留原建议 ID，标记 reviewable（待运营审阅），不代表已审批或线上应用。未来后台交付须通过此检查，当前本步仍是独立人工测试。

### 步骤 6 的交付与恢复

- 6A 先保存不可变分析包，再提供只读已有分析的交付函数；不在交付重试中生成建议。记录标识按完整内容摘要产生，重复保存相同内容使用同一记录；不同分析保留为不同记录，不覆盖旧证据。这不是后台按信号去重的替代，生成任务去重由后续后台步骤负责。
- 每次交付重新执行 5B，并先保存检查与尝试记录，之后才提交到 LocalRecommendationSink；接收异常或回执不符标记交付未确认，不能推断接收端没有保存。结果写盘失败直接报错，重试沿用已保存建议 ID，由接收端去重。
- 保存各次尝试及回执，不覆盖历史；后续配置变化只影响新尝试，不能抹掉旧接收事实。本地接收始终标为 mock/applied=false。
- 后续再接后台信号派发、样本读取、生成并发/重试、确认信号和运营可读报告；6A 本身不确认 Redis 信号，不启动模型请求。
- 6B 用同一流程入口串联上述模块。稳定信号身份定位处理目录，完整输入另存并拒绝同身份换内容；本机文件锁防止同信号并发生成。分析前保存开始记录和材料，分析后先保存完整结果再建索引。交付重试自动找回原分析，不让用户手工传编号；有开始记录但无完整结果时标为 analysis_unconfirmed，不自动重调模型。材料读取故障发生在分析之前，可再次尝试。当前仅本地 mock 串联，后续仍需接既有后台任务、真实材料和信号确认。
- 6C 新增 LOCAL SQLite 只读任务读取器，按应用、流程和最多 20 个信号引用告警查询，保留所有状态与重复版本，不按任务创建时间冒充接收窗口。超过 100 行或 8 MiB 返回材料上限时明确失败，不截取部分版本。原告警无效时保留异常行，由 4A 排除该样本；可选历史响应无效时保留原告警并记录 stored_response_omitted。末尾诊断只读取最近任务引用并输出数量，不产生突增信号或模型请求。
- 6D 将 pending → SignalProcessor → acknowledge 串成一次调用，按模式、命名空间和规则作用域校验信号。任务尚未提交时返回 materials_pending，材料全部不可用时返回 materials_unavailable；二者都在分析开始记录之前结束，不固化空材料。完整输入、分析内容和交付结果均核对已落盘后才按原 signal_id 确认；确认超时为 ack_unconfirmed，不断言信号仍在。交付重试复用原分析。此步人工计数器测试不代表后台调度、真实 Redis 消费已上线。


- 6E 先只读核对启动方式：原源码包包含 local_run.sh、local_run.detector.sh，没有用户口述的 run_local.sh。local_run.sh 启动 tasks.task.app、单并发 periodic_queue worker 和独立 beat，但不消费 default 队列。内网实际版本、可见进程及所属项目需核对，不能直接照源码启动脚本或重复起 worker。
- 6F 新增后台适配与轮转执行器：任务注册到 tasks.task.app，LOCAL beat 每30秒向 periodic_queue 发一个 expires=25秒的 tick；代码安装时独立分析配置默认关闭。后台复制环境后读取监测配置，验证环境变量及已加载应用均为LOCAL，固定本机SQLite和本机模型代理；在分析开始记录之前取得原共享模型并发槽。每tick查询当前目录最多256个作用域、只处理一个信号，固定所读快照并按原身份确认。持久游标轮转，60秒间隔，最多3次尝试后保留信号并暂停该信号自动重试；模型槽繁忙不消耗次数，已阻断/分析未确认立即暂停。显式重置只解除后台重试暂停，不删除原分析或自动重新生成。内网已回传适配测试、演示及独立Celery注册通过；启用、broker及真实模型链路仍待验证。规则目录移除后的旧信号不在当前枚举范围。
- 6W替代上述失败恢复行为：明确模型失败按配置建新attempt，成功交付补投沿用原分析；次数耗尽先保存分析、交付与finalized记录并复读一致，再确认待办。开始后未收到响应/未完整保存结果保持unconfirmed，不自动重发。CLI按规则或all显式retry/release，旧失败升级不静默重调。维护扫描与动作使用同一scheduler锁，SET NX和条件确认保留新pending；纯材料等待不消耗失败次数，部分材料可继续并记录缺失。入口计数不被维护命令改变。
- 6G 在分析关闭状态验证真实调度：原local_run.sh终端Ctrl+C后等待全部子进程退出，检查版本、开关及同应用旧进程，再按原脚本以LOCAL重启。API和代理不重启，不另起脱离原脚本管理的worker/beat。贴回beat定时派发与worker的analysis_disabled日志，之后再进入分析启用。原beat启动还会派发既有Skills同步，不能将后台重启称为零外部操作。
