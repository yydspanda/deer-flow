# SOC Agent Reporting FAQ / 汇报常见问题与回答

## 1. 这和直接调用一次大模型有什么区别？

这里的“直接调用一次”是被对比的简易方案，不是本系统固定只能调用一次。常规告警默认使用一次主分析；关键角色存在
实质疑点且复核开关开启时，可增加一次窄范围复核；Business Lesson 草拟和 Lead Agent 调查则属于独立交互。系统还补齐
输入适配、状态机、结构校验、证据引用、持久化、失败恢复、权限、人工审核、Memory 生命周期和动作审计。模型是 Runtime
中处理不确定性的节点，不是操作系统。

## 2. 为什么不是一个全能 Agent 自己决定下一步？

实时告警要求可预测、可重放和可控成本，所以主流程由 Runtime 固定；运营对话和开放式调查使用 Lead Agent 动态选择
Skill/MCP/Sub Agent。二者共享 service、证据和权限，不各写一套。

## 3. LLM 到底做了什么？

它综合类型化证据和安全知识，判断场景、攻击阶段、网络方向、攻击者/受害者、当前风险、证据缺口和建议动作。
字段解析、Schema、状态、权限、持久化和外部执行由代码负责。

## 4. 上游预警都不相信，还怎么研判？

系统相信规则确实命中，也相信 Adapter 明确声明的字段语义。它不会无端否定上游；但“规则命中”“已造成影响”与
“允许自动封禁”是三个不同命题，分别保留证据和权限边界。

## 5. 为什么同一个 rule_code 还要分组？

rule_code 是粗分类。平安 `红队IP监控` 同时覆盖 OpenVPN、PLC 漏洞、HTTP 信息泄露等不同语义。若只按 rule_code
复用结论，一条误报经验会让整条规则失效。行为指纹用于区分真正可复用的同类模式。

## 6. 是否每天一万条告警就产生一万条 Memory？

不会。每条新告警最多形成去重后的 Pattern Observation；只有同类模式达到支持数和一致性门槛才产生 Candidate，
仍需运营确认后才成为 Memory。单条高价值样本也可由运营显式提炼，但不会自动确认。

## 7. Memory 怎么影响新告警？

先按租户（所属企业/客户）、有效期、状态和类型化特征召回，再校验 detection key、行为指纹和人工收窄条件。相关但不精确的经验仅作为
context-only；精确且被审核人授权为 directive 的经验才进入 Memory Decision，并保留 Base 与 Effective 前后对比。

## 8. Memory 会不会污染？

通过 Candidate 审核、Business Lesson 六部分结构、适用条件、失效条件、检索开关、directive 开关、版本化修订和使用历史
控制。发现问题时先暂停旧 Memory，再创建 revision candidate，不原地篡改历史。

## 9. 模型输出 JSON 不稳定怎么办？

模型输出已收缩为核心结论和引用 ID。Runtime 负责补全固定结构，并允许局部 repair/degrade；可选角色区块失败只阻断依赖
精确目标的动作，不让整份有效 verdict 回退成 stub。传输/容量失败则明确标为可重试失败。

## 10. 模型结论能直接封禁吗？

架构允许在策略明确时自动执行，但不是模型一句话就执行。Effective Decision 后还要经过目标一致性、动作策略、Provider 配置、
授权级别、幂等和审计。演示环境外部动作固定 disabled。

## 11. 换其他厂商还能用吗？

可以。平安字段、知识和策略由独立适配层承载；通用 Runtime 只消费统一的数据与能力协议。新厂商主要新增 Adapter、
Provider 和租户配置，而不是修改整条研判流水线。

## 12. 为什么要分成 Skill、MCP、企业知识、Memory 和 Policy？

因为它们回答的是五个不同问题：Skill 是“怎么分析”，企业知识是“这个组织有哪些稳定事实”，Memory 是“过去审核确认了什么”，
MCP/Provider 是“现在能查什么或执行什么”，Policy 是“最终允许怎么处置”。混在一个 Prompt 里后，事实无法独立失效、经验无法审核修订、
工具失败会污染推理，甚至自然语言可能意外获得执行权；分层后，每项能力都能按企业独立替换、版本化、审计和关闭。

## 13. 现在准确率是多少？

还不能负责任地给生产准确率。当前 4,343 条中历史运营“忽略/转交”是流程结果，不是独立真值。下一阶段需由具名运营专家
审核代表性样本，按来源和场景分别评测，并在 Shadow 中持续监控漂移。

## 14. 现在是否可以上线？

可以在内网 DEV 演示和进入只读 Shadow 准备，不能宣称生产就绪。真实 Provider、Kafka/PostgreSQL/K8s、容量、安全、SLO、
真实质量门和 rollout owner 尚需完成。

## 15. 价值怎么量化？

Shadow 阶段统计：每类告警人工平均时长、自动补全证据比例、Memory 精确命中率、命中后复核率、误改判率、ReviewQueue 比例、
P50/P95、token/成本和错误自动化数量。用这些指标决定是否扩大试点，而不是用 Demo 主观评分。

## 16. 为什么还需要人工？

人工不再逐条从零研判，而是治理高价值 Candidate、处理真正冲突/证据缺口、批准高风险动作和提供少量质量真值。目标是把人力
从重复点击转移到经验治理和异常决策。

## 17. 哪些能力现在还是 mock？

当前语料页面明确显示内网安全能力接口关闭/模拟、企业专属策略关闭、外部动作关闭。真实资产、威胁情报、安全标签和
内网工作流已有接口边界，但必须在内网完成成功、查无、失败和超时四类真实验收后，才能关闭真实接入 Gate。

## 18. 为什么不用 relatedAlertList 直接判断？

旧关联预警多为干巴巴结论、反馈质量不稳定且可能相互冲突。它可作为弱历史上下文，但不能替代当前告警证据或 Confirmed Memory。
新方案将可复用经验提炼为有适用边界和审核来源的 Business Lesson。

## 19. 下一阶段最需要什么资源？

一是内网只读接口和凭证用于 Provider 验收；二是少量稳定运营专家用于 Candidate 与质量样本审核；三是 Shadow 所需运行环境和
指标采集。暂时不需要先建设大规模自动封禁。
